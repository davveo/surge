# 容量规划、选型与验收

按「同时在线」而不是注册量建模。发送 QPS 按在线用户每分钟约 0.3% 发言、群平均扇出 10 估算峰值，并留 3 倍余量。模型日期：2026-08-19。

## 阶段容量

| 指标 | P0 | P1 | P2 | P3 |
|---|---|---|---|---|
| 同时在线 | 1 万 | 10 万 | **100 万** | 300 万+ |
| Gateway | 2 台 | 4 台 | **16–20 台 × 约 60k 连接** | 就近接入多集群 |
| 峰值发送 QPS | ~50 | ~500 | **3–5k** | ~10k |
| 峰值投递 QPS（扇出后） | ~200 | ~4k | **50–100k** | ~150k |
| 基础设施 | 单区 · 1 MySQL · 1 Redis | 单区 · MySQL 主从 · Redis 哨兵 | 多 AZ · TiDB · Redis Cluster · Kafka | 多 Region · 独立 RTC |

P2 连接内存粗算：1M × 20–40KB ≈ 20–40GB，摊在网关集群上，而不是单机。

心跳必须 30–45s。若 1M 连接 × 5s ping，空转约 20 万包/秒，会先打满 CPU。

## 技术选型

与本仓库（Go）对齐。

| 层 | 选型 | 不选什么 |
|---|---|---|
| 前端 | React + TS + Vite + Dexie(IndexedDB) + Protobuf | 把消息权威状态只放内存 |
| 网关 | 自研 Go（netpoll/gnet）+ 二进制帧 | 用 Node 长连接硬顶 100 万 |
| 业务 | Go + gRPC；HTTP 只给 CRUD / 上传凭证 | 网关里写业务逻辑 |
| 关系/账号 | P0 MySQL，P2 TiDB | 把消息正文塞进 MySQL 大表不拆 |
| 消息 | 按 cid 分片的追加存储（TiDB 分区或独立消息库） | Mongo 单集合无限涨 |
| 路由/seq | Redis Cluster | 用 DB 做在线路由 |
| 异步 | P1 可进程内；P2 Kafka 必上 | 用 Redis Pub/Sub 当持久扇出 |
| 媒体 | OSS + 预签名 PUT + CDN | 文件字节走应用服务器 |

## 风险与验收

| 风险 | 为何致命 | P2 必须验收 |
|---|---|---|
| 网关与业务耦合 | 连接扩容会拖垮落库 | 杀 30% 网关节点，消息不丢、路由 10s 内收敛 |
| 群写放大 | 1 条群消息变成 N 次正文写入 | 2000 人群发送 p99 落库 &lt; 50ms，inbox 异步 |
| 无 seq 同步 | 断线、多 Tab、多设备必乱序/丢提示 | 断网 5 分钟后重连，会话与未读与服务器一致 |
| 心跳过密 | 1M 连接 × 5s ping = 20 万包/秒空转 | 心跳 30–45s，空闲 90s 踢，CPU 可解释 |
| 媒体打满网关 | 图片走 WSS 会挤掉信令 | 上传只走 HTTPS 预签名，消息里只留 object key |

## SLO

| 指标 | 目标 |
|---|---|
| 连接成功率 | 99.9% |
| 发送 ACK p99 | &lt; 200ms |
| 在线推送 p99 | &lt; 500ms |
| 网关故障后路由收敛 | &lt; 10s |
| 2000 人群落库 p99 | &lt; 50ms |
